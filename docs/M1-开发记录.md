## 2. 开发环境（WSL + D 盘，重要）

工程在 `D:\Project\app`（WSL: `/mnt/d/Project/app`），但依赖装在 ext4 以避开 drvfs 的 I/O 慢：

```
node_modules  ->  ~/.nm/app/node_modules        （软链，真实目录在 ext4）
```

**踩过的坑与结论：**

1. **不要**在 `D:\Project\app` 放 `.npmrc` 指定 `virtual-store-dir`。
   它会让 pnpm 把 `node_modules/.bin/*` 里的调用路径写成
   `"$basedir/../../../.nm/app/node_modules/..."`，从 D 盘看就是
   `/mnt/d/Project/.nm/...` → `next` 启动直接 `MODULE_NOT_FOUND`。
2. 正确做法：装依赖在 `~/.nm/app` 里跑，然后把 `package.json` / `pnpm-lock.yaml` 拷回 D 盘；
   装完执行 `/tmp/fixbins.sh`（把 `.bin` shim 里的相对路径改写为绝对路径）。
3. 新增 shadcn 组件：在 ext4 副本 `~/shadcn-build`（带 `.npmrc` + 软链 node_modules）里跑
   `pnpm dlx shadcn@latest add <name> -y -o`，再把 `src/components/ui/*` 拷回 D 盘。
4. drvfs 上 **Next 的文件监听不可靠**：改完代码如果没生效，直接重启 dev（`/tmp/dev.sh`，日志 `/tmp/dev.log`）。
5. 启动：`setsid sh /tmp/dev.sh` → http://localhost:3000（`/` 首页、`/canvas` 画布）。

### 步骤 2 · 持久化防抖（T1.9）✅

**问题**：`persist` 默认在每次 state 变化时同步写盘。拖动节点 / 拉线时 `onNodesChange` 每帧触发，
等于每帧 `JSON.stringify(整个节点图)` + 一次同步 localStorage 写入。

**新增 `src/lib/debouncedStorage.ts`**
- `createDebouncedLocalStorage(delay)` 返回 `{ storage, flush, writes }`
- trailing 合并：高频繁写入只保留最后一份快照，400ms 静默后才落盘
- `getItem` 读到待写入快照时以内存为准，避免读回旧值
- `removeItem` 会取消待写入，避免删除后又被写回
- 无 `localStorage`（SSR / 隐私模式 / 配额满）时静默降级，不抛错
- 注册 `beforeunload` / `pagehide` / `visibilitychange(hidden)` → `flush()`，
  保证关页面、切标签、刷新时不丢最后一次拖拽

**接入**：`canvasStore` 的 persist 选项加 `storage: createJSONStorage(() => canvasPersistence.storage)`；
dev 下额外暴露 `window.__canvasPersistence`（`flush()` / `writes()` 可观测）。

**验证**
- `scripts/check-persist-debounce.ts`（`pnpm tsx scripts/check-persist-debounce.ts`）：
  200 次 `setItem` → 真实写盘 0 次；窗口结束后 1 次且内容是最后一份快照；`flush` 立即落盘；
  `removeItem` 取消待写入；SSR 下不抛错 —— 全部 PASS
- **真实浏览器 CDP 端到端**（`localhost:3000/canvas`）：
  - 连续 30 次 `addNode` → 真实 `localStorage.setItem` 只发生 **1 次**（旧实现是 30 次）

### 9.4 浏览器自动化环境（重要，修好了之前的错误结论）

**之前记录的「React Flow 只认真实指针事件 → 无法自动化」其实是环境问题，不是 React Flow 的限制。**
这次摸清了真实情况：

**① 连接方式：harness 默认探不到浏览器，要显式指定 endpoint**
本机浏览器是 **Windows 上的 Edge**，DevTools 端口在 **WSL 网关**上，不在 `127.0.0.1`：

```bash
# harness 只探 127.0.0.1:9222/9223 → 报 chrome-not-running
# 实测 172.31.96.1:9223 返回 200（172.31.96.1 = `ip route` 的默认网关）
export BU_CDP_URL="http://172.31.96.1:9223"
browser-use <<'PY'
print(current_tab())
PY
```
> 拿网关 IP：`ip route | awk '/^default/{print $3; exit}'`
> 另外 **不要** `pkill -f browser-use`（会连 daemon 一起干掉，之后要重新用 BU_CDP_URL 起）

**② 这个 attached tab 永远 `visibilityState === 'hidden'`，`requestAnimationFrame` 不执行**

### 9.5 环境补充：hidden 标签页里 ResizeObserver 也是冻结的

  DOM 会一直保留；之后标签页转为 hidden，一旦刷新就再也测不到了
- **推论**：依赖 DOM 的边渲染断言必须在可见标签页做，或先注入 `handles`

另外实测到：**后台标签页的 `setTimeout` 会被节流**，400ms 的防抖写盘在后台可能远晚于 400ms 才落盘

### 9.6 环境补充：hidden 标签页里「连续事件」的 React 更新不会 flush
排查「拖拽提示不出现」时挖到的关键事实：**在 hidden 标签页里，
由 `dragover` / `dragleave` 这类连续事件（continuous priority）触发的 React 状态更新永远不会落地**
（React 把它排成非紧急工作，等下一次可绘制机会；而 rAF 冻结 → 没有下一次）。

对照实验（同一段代码、同一个标签页）：
| 触发方式 | 结果 |
| --- | --- |
| `js()` 里直接调 `onDragOver(...)`（默认优先级） | ❌ 6s 后提示层仍未渲染 |
| `el.dispatchEvent(new DragEvent('dragover'))`（连续优先级） | ❌ 同上（但 `preventDefault` 确实被调用了） |
| **在 `click` 监听器里调 `onDragOver(...)`**（离散优先级） | ✅ 提示层立刻出现 |
| `setPaletteOpen()` 等 zustand 更新（默认优先级） | ✅ 正常渲染 |

结论与用法：
- **代码没问题**，真实浏览器里 `dragover` → 下一帧就会渲染
- 但**要在这个环境里验证「连续事件驱动的 UI」**，得把它塞进 `click`/`keydown` 之类的离散上下文里触发
- `drop` 是离散事件，所以「拖拽落点」这类断言**可以**直接验证 ✅
- `Page.bringToFront` / `browser-harness` 的 `activate_tab()` 都**不能**让标签页变可见（浏览器窗口本身不在前台），
  `visibilityState` 仍是 `hidden`

### 步骤 9 · 下游节点自动带上上游产物（连线即上下文）✅

**调研（看 LibTV 截图得出的实现方式）**

**新增 / 改动**
- `src/lib/upstream.ts`：
  · `directUpstreams`：直接上游（不含隔代）
  · `upstreamContexts`：已就绪（succeeded + output）的上游产物
  · `pendingUpstreams`：还没产物的上游（拦截用）
  · `nodeDisplayName`：标题+序号（“文本节点 1”）
  · `describeOutput`：把上游产物压成短摘要
- `canvasStore.buildMockOutput(node, upstreams)`：抽成纯函数构建 mock 产物——
  · 文本/脚本产物 JSON 里加 `upstream_context`（from/kind/summary），并附可读注释
  · 媒体产物的 SVG 里加一行「基于上游：…」
  · M6 接真模型时，这套上下文直接作为请求 context
- `runNode`：开跑前 `pendingUpstreams` 非空 → 红色提示「上游节点还没生成产物：…」并中止，
  节点保持 idle；否则注入 `upstreamContexts` 再生成
- `runAll`：入度排序改为 **Kahn 真拓扑排序**（有环时提示而不是静默漏跑/误拦）

# T3.5 第三步：运行时变量渲染集成

## 设计

- worker：执行时从快照取生效值 → 再次渲染 → **缺失变量在这里拦截 failed** →
  用渲染后 prompt 算 inputHash、调 provider
